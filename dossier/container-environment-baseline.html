What was measured

The audit harness inspected a Linux host running Docker, once against a hardened reference container and once against a deliberately weak companion environment created for this exercise. A third read-only run audits a daemon-configuration fixture. The harness reads daemon configuration, file permissions, audit rules and the runtime flags of running containers. It installs no agents and changes nothing.

What this proves

  • The harness discriminates: five controls that pass on the reference container flip to FAIL on the weak environment — AUD-08, AUD-10, AUD-11, AUD-12, AUD-13. A sixth failure, AUD-04 (default ulimits), is a daemon-level setting that fails in both environments.
  • The reference container is hardened: non-root, read-only root filesystem, memory and CPU limits, no privileged flag, no docker-socket mount.
  • The remaining baseline failure is configuration, not code: default ulimits are not declared at the daemon level (F-01, severity Low — see section 05).
Scope note. These are lab measurements from a Docker Cloud Sandbox (2 vCPU, 4 GB, Linux 6.12.114 aarch64, Docker 29.9.3). They are not timings measured on a client fleet. Control coverage, raw evidence and the exact commands are included so the result can be reproduced or extended.

02 · Method and control coverageYLG-AUD-2026-084

Harness

A zero-dependency POSIX shell harness (lab/cis-audit/audit.sh) checks 13 CIS-aligned controls across five areas, plus a separate connectivity check. It emits human-readable output and JSON, exits non-zero when a control fails or the daemon cannot be reached, and never writes to the host. The same command runs in CI or on a live host.

Execution
Read-only introspection via docker inspect, filesystem metadata and daemon configuration
Dependencies
POSIX sh, docker CLI, coreutils — no agents, no sidecars, no network calls
Output
JSON + terminal table; deterministic, machine-readable, suitable for CI gates
Weak demo
lab/cis-audit/demo-weak.sh creates privileged, root, writable, unlimited containers and mounts the docker socket, then cleans up

Control coverage

CIS-aligned, not a CIS certification. AUD-01 … AUD-13 are Yalgar's own identifiers. They are grouped by the areas the CIS Docker Benchmark covers (host, daemon, files, images, runtime), but this dossier does not assert exact CIS rule numbers or a benchmark edition, because those were not verified against a published edition when the evidence was collected. This is not a certifying CIS assessment: the harness inspects running containers and host configuration, while a full CIS assessment also covers build pipelines, image provenance and organisational process. Where the host cannot evaluate a check, it reports N/A and never counts it as a pass.

Environments compared

Hardened reference

Reference image, non-root user, no daemon agent, run with --read-only, --memory 512m --cpus 0.5 and --security-opt no-new-privileges.

Weak companion

Two containers, intentionally bad: --privileged --user 0:0, apparmor=unconfined, a docker-socket mount, no limits and a writable root filesystem.

Running the same harness against both environments shows that each check discriminates rather than passing for trivial reasons (for example, no containers at all).

05 · Findings and remediationYLG-AUD-2026-084

Findings

Each finding is reproducible from the evidence tables; remediation is scoped and verifiable.

IDControlFindingSeverityRemediation
F-01 AUD-04 Default ulimits are not enforced
Recorded: default-ulimits is missing from daemon config		 Low Declare default-ulimits (nofile/nproc) in the Docker daemon configuration and restart the daemon.
F-02 AUD-08 Containers run as root
Recorded: root/default user: cis-weak-2		 High Add an explicit non-root USER in the image and drop privileges in the runtime definition.
F-03 AUD-10 Writable root filesystem
Recorded: writable rootfs: cis-weak-2 cis-weak-1		 Medium Run containers with --read-only and mount tmpfs for writable paths.
F-04 AUD-11 Privileged container
Recorded: privileged: cis-weak-1		 High Remove --privileged; grant only the specific Linux capabilities required.
F-05 AUD-12 No memory or CPU limits
Recorded: unlimited: cis-weak-2 cis-weak-1		 Medium Set --memory and --cpus (or compose deploy.resources) for every service.
F-06 AUD-13 Docker socket mounted into a container
Recorded: socket mounted: cis-weak-2		 Critical Remove the socket mount; use a restricted API proxy if container control is genuinely required.
F-07 AUD-05 Remote API without TLS
Recorded: no remote TCP host configured		 Critical Remove the TCP host or enable TLS with client certificate verification.
F-01 severity: Low. AUD-04 is a daemon-level default. The reference container already declares its own memory and CPU limits (AUD-12 PASS), so the missing default only changes the fallback for containers that declare no limits at all. The host runs a single reference workload, not untrusted multi-tenant containers, so an exhausted file-descriptor or process table degrades one workload rather than granting privilege. Residual risk: a future container that sets neither a ulimit nor a memory limit could exhaust host-wide resources and affect co-tenants; declaring default-ulimits (nofile/nproc) and per-container limits closes that path.

Remediation order

  1. Critical first: remove the docker-socket mount (F-06) and any remote API without TLS (F-07). These two turn a compromised container into host compromise.
  2. Then privilege: drop privileged mode (F-04), declare non-root users (F-02), and make root filesystems read-only (F-03).
  3. Then resilience: set memory/CPU limits (F-05) and default ulimits (F-01).
  4. Verify: re-run the harness after each change; the finding must move to PASS.

The reference container already passes AUD-08 through AUD-13. The only open baseline item is F-01 (daemon-level default ulimits), which is a host configuration change rather than an application change. F-07 is not reproducible from the container environments alone; its evidence is on the next page.

05 · Findings and remediation — F-07 evidenceYLG-AUD-2026-084

Daemon-config fixture

F-07 (remote API without TLS) cannot be reproduced from the two container environments: it needs a daemon configuration that exposes the remote API. The harness audits a fixture file read-only with --daemon-config, so the recorded run audits lab/cis-audit/weak-daemon.json instead of changing a host daemon. What the fixture does and does not prove. It proves that the harness reports a remote API configured without TLS as FAIL when one exists, and that the recorded run captures both the daemon-level TLS failure (AUD-05) and the world-readable fixture file (AUD-03). It does not prove that a client host is exposed: the fixture is deliberately unsafe. F-07 stays open until the daemon configuration is changed or a TLS-terminating proxy is enforced, then verified with the same command.
Why 6 WARN? The fixture run has no running containers, so the six runtime checks (AUD-08 … AUD-13) report "no running containers to evaluate". WARN is neither PASS nor FAIL and is never counted as a pass. The run summary covers all 14 recorded rows: 13 CIS-aligned controls plus the separate connectivity check.

07 · Disclosure and limitationsYLG-AUD-2026-084

Disclosure

This public excerpt contains the control coverage, measured results and remediation guidance. The following are withheld and available to vetted clients under a controlled release:

  • the internally extended rule set and organisation-specific scoring model;
  • client infrastructure topology and sanitized vulnerability reproduction details;
  • the continuous-audit CI configuration used on client pipelines.

Limitations

  • Measured in a Docker Cloud Sandbox, not on client infrastructure.
  • The control set is CIS-aligned and uses our own AUD identifiers; it is not a certifying CIS assessment, and no exact CIS rule numbers or benchmark edition are claimed.
  • Single host; no fleet-wide sampling or historical drift analysis.
  • auditd and AppArmor could not be evaluated on this kernel (reported N/A, not PASS).
  • The daemon-config fixture is deliberately unsafe; it demonstrates detection, not a client's daemon configuration.
  • The companion weak environment is intentionally bad; its findings demonstrate detection, not a client's posture.
  • Performance of the application was smoke-tested, not load-tested.

Next steps for a client engagement

  1. Scope the hosts, images and release gates to include.
  2. Run the harness read-only; agree the control set and scoring.
  3. Deliver prioritised remediation with verification after each change.
  4. Optional: wire the harness into CI as a pre-deployment gate.
